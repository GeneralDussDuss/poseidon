# POSEIDON firmware — full audit (2026-08-23)

Two-phase multi-agent audit (16 subsystem auditors + adversarial verification). Every finding below was re-read against the actual source and confirmed reproducible; unverified/refuted candidates were dropped.

**28 confirmed defects** — 2 critical, 11 high, 8 medium, 7 low.

Branch audited: `ui-foundation`. Biggest theme: the **T-Embed port** reuses Cardputer-era constants/pins (both criticals), followed by unbounded parsing of attacker-controlled RF/network input and cross-task use-after-free / missing locks.


## CRITICAL

### `src/sd_helper.cpp`:23  · resource · _board_

**SD/radio SPI clock+data pins are hardcoded to the Cardputer's SCK=40/MISO=39/MOSI=14, which on the T-Embed board are the I2S speaker word-clock (GPIO40), PDM mic clock (GPIO39) and the WS2812B LED-ring data line (GPIO14) â€” so the SD bus, the audio amp, and the LED ring all fight for the same three pads.**

On a POSEIDON_BOARD_TEMBED build, boot runs tembed_speaker_init() (main.cpp:150, I2S driver claims GPIO40 = TE_I2S_WS), then sd_mount() (main.cpp:163) calls sd_spi.begin(SD_SCK=40, SD_MISO=39, SD_MOSI=14, ...) GPIO14 and GPIO40 are now double-claimed via the GPIO matrix (last writer wins the pad). Runtime result: every LED animation frame drives GPIO14, corrupting/blocking any SD MOSI transfer, and any sound played through M5.Speaker toggles GPIO40 (SD SCK), corrupting the SD clock mid-transaction â€” SD writes of credential/capture CSV logs return garbage or hang on the SPI transaction semaphore, and audio/LED output glitch whenever SD is touched. cc1101_hw.cpp:47 (ELECHOUSE_cc1101.setSpiPin(40,39,14,...)) puts sub-GHz on the same colliding pads, so CC1101 also never works on T-Embed and stomps the LED/audio pins. The board's real SD/radio bus (board_tembed.h TE_SPI_MOSI=9/MISO=10/SCK=11, TE_SD_CS=13, shared with the display) is never used by sd_helper â€” the CS pins were board-gated but the bus SCK/MOSI/MISO were not.

### `src/net_helpers.cpp`:47  · heap · _heap-input_

**net_http_get reads an unbounded HTTP response line into an Arduino String, and the '512-byte' cap is checked BEFORE the append so one huge line bypasses it â€” attacker-controlled LAN server can exhaust the Cardputer's ~115 KB internal heap.**

net_cctv / net_lanrecon call net_http_get against a rogue or hostile LAN device (camera/router) they are fingerprinting. The server replies with a valid 'HTTP/1.0 200 OK\r\n' status line, then emits a header or body line containing NO '\n' for hundreds of KB. `String line = c.readStringUntil('\n')` (line 47) accumulates the whole stream one char at a time into a single String until the 1 s stream timeout or socket close â€” at LAN speed that is hundreds of KB to MB. Even the persistent buffers are not actually bounded: `if (out_headers->length() < 512) *out_headers += line;` (line 57) and the body equivalent (line 58) test the length BEFORE appending, so when length is 511 the entire multi-hundred-KB `line` is appended. On the ~115 KB internal SRAM budget this drives heap/largest-block to zero, causing allocation failures across the active WiFi stack and a watchdog reboot/hang. Note rf_preflight()/heap_budget never gates this path, so the heap-budget subsystem does not protect against this exhaustion vector. Fix: cap readStringUntil accumulation (read fixed-size chunks with a hard byte ceiling) and check the length limit before, not after, growing line/out_body/out_headers.

### `src/mesh/meshtastic_pb.cpp`:143  · memory-safety · _mesh_

**Protobuf length bounds checks (read_length line 143 and skip_field line 129) use `*p + n > end` where n is a 64-bit attacker-controlled varint length; on the 32-bit ESP32 this pointer addition wraps around the address space, so a huge length passes the check and defeats all bounds validation in the decoder.**

An attacker transmits a single LoRa frame on the public Meshtastic LongFast default channel (the AES PSK is hardcoded/public in meshtastic.h, so no secret is needed). After AES-CTR decrypt in rx_task, mesh_pb_decode_data parses the Data proto. The attacker includes either an unknown field with wire type 2 or a payload field whose length varint is ~0xFFFFFF00. In skip_field/read_length the check `*p + n > end` computes pointer+n in 32-bit arithmetic, wraps below `end`, and returns true instead of rejecting. skip_field then does `*p += n`, advancing the parse pointer out of the buffer so the next read_varint dereferences memory outside the 260-byte `ctext` stack array (OOB read -> LoadProhibited crash of the mesh_rx task). Via read_length in the payload case with a near-max-length packet, the subsequent clamped 200-byte memcpy starts near the end of ctext and reads past ctext[260] into adjacent stack, copying stack bytes into the message text shown in the UI/serial log (info leak). Net effect: remote single-packet denial of service (RX task crash) and/or stack info disclosure, unauthenticated, over RF. Fix: compare against remaining length, e.g. `if (n > (uint64_t)(end - *p)) return false;`, never `*p + n > end`.

### `scripts/prepare_release.sh`:54  · build · _satcom-tests-tools_

**TRIDENT factory image merges the ESP32-C5 second-stage bootloader at flash offset 0x0, but the ESP32-C5 ROM loader reads the second-stage bootloader from 0x2000 (like ESP32-P4/C61), not 0x0 as on C3/C6/H2. The resulting trident-factory.bin has no valid image header at 0x2000.**

### `src/features/ble_extras.cpp`:217  · concurrency · _ble_

**BLE sniffer writes the SD File object from the NimBLE scan-callback task while the main task closes it on exit, with no synchronization â€” a use-after-close / SD-corruption race.**

### `src/cc1101_rmt.cpp`:204  · resource · _hw-drivers_
